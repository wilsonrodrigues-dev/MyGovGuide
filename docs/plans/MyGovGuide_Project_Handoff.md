## 1. Project summary

- **Name:** MyGovGuide (final, locked).
- **Tagline:** "Government Information, In Your Language".
- **Type:** Solo MCA final-year capstone. Synopsis submitted to Ms. Jayashree (MCA Dept., SJEC), June 2026. Graduation March 2027.
- **What it is:** A mobile-first web app that helps Indian citizens discover government schemes, understand forms and public notices in simple regional language (English / Hindi / Kannada), check eligibility, and get personalized scam alerts. AI (Gemini) simplifies official text; every simplified result is shown **next to the original clause and official source link**.
- **Problem:** Government info is dense, legalistic, mostly English/Hindi, spread over many sites. Rural, elderly and semi-literate users struggle to find schemes, read notices, and fill forms.
- **Not claiming novelty.** Positioning:
  1. Regional depth (Kannada + Hindi + English, Karnataka focus)
  2. Source transparency (original clause + official link always shown)
  3. No-login onboarding
  4. Own live scraping pipeline (not static content)
  5. One profile personalizes everything (schemes + scam alerts + notices + change alerts)
  6. Documented sustainability / business model
- **Precedents compared against:** myScheme, UMANG, Jugalbandi (Microsoft/AI4Bharat/OpenNyAI, WhatsApp, now deprecated), SevaApply, India Help, Vak Sahayak, Kisan e-Mitra, Samadhan Didi.

## 2. Users

- **Citizens:** farmers, students, senior citizens, other beneficiaries. Varying literacy; regional language; mobile phones.
- **Intermediaries:** CSC operators, NGO staff, family members searching on behalf of a citizen. Real end user is often the intermediary.
- **No login for any core feature.** Account is optional and only for bookmarking.

## 3. Features (9 MVP features + optional bookmarking)

### F1. Onboarding & Personalization
- Captures **state, category, language** (typed/selected, or spoken).
- Categories (suggested list): Farmer, Student, Senior Citizen, Woman, Entrepreneur/Small Business, Worker/Labourer, Person with Disability, General.
- No login. Profile stored server-side under an anonymous `deviceId` (UUID kept in localStorage) and mirrored in localStorage/React context.
- Every other feature reads this profile; user never re-enters it.
- Editable later from a Profile/Settings screen.

### F2. Scheme Discovery & AI Simplification
- Search box (text or voice) + filters (state, category).
- Backend filters schemes by profile (state or "All India", category) + text match.
- For each scheme: show **simplified text in the user's language**, the **original clause**, and the **official source link**.
- Simplified text is generated by Gemini on first request per language, then **cached** in `schemes.simplifiedText[lang]`.

### F3. Forms Library & Forms Explanation
- Searchable library of application forms linked to schemes.
- Opening a form shows **field-by-field guidance**: what the field means, what to write, example, where to get the document. Generated by Gemini per language and cached in the form's `fields[].description[lang]`.
- Link to the official form PDF/page.

### F4. Eligibility Gap Analyzer
- User picks a scheme, answers a short question set (age, income, category, state, gender, occupation, land holding, etc. — driven by the scheme's `eligibilityRules`).
- **Deterministic rule engine** (not LLM) decides pass/fail per criterion.
- Result: eligible / not eligible, per-criterion pass/fail, **what is missing**.
- Gemini only **explains** the already-computed result in plain language. It never decides eligibility.

### F5. Notice-to-Action
- User pastes notice text (or uploads an image/PDF — see §17 for the OCR decision).
- Gemini returns: plain-language **explanation**, and an **action checklist** with items and due dates (when present in the notice).
- Checklist items can be ticked off in the UI.

### F6. Change Radar
- Pipeline diffs each scheme's newly scraped version vs previous version.
- Detected changes are matched against stored profiles (state, category, and bookmarked schemes).
- Matching users get a personalized in-app notification ("Scheme X changed — you may now be eligible"). See §17 for the delivery-channel issue.

### F7. Voice Input & Readback
- **Input:** Web Speech API `SpeechRecognition` (`en-IN`, `hi-IN`, `kn-IN`). Bhashini ASR as regional-language fallback.
- **Readback:** `speechSynthesis` (browser TTS). Bhashini TTS as fallback where device has no Kannada voice.
- Mic button on search, onboarding, eligibility and notice screens; "Read aloud" button on every result.

### F8. Scam Alerts & Showcase
- Alerts sourced from CERT-In and Cyber Dost, stored in `scamAlerts`.
- **Personalized feed** (matches profile category) and a **public showcase page** (no profile needed, browsable by anyone).
- Alert text shown in user's language (Gemini-translated, cached).

### F9. Bookmarking (optional account)
- Register/login (phone + password, JWT + bcrypt).
- Save schemes and forms; list and remove bookmarks.
- Only feature that requires an account.

### Out of scope (Future Scope — do NOT build)
WhatsApp bot, OCR scam-screenshot analysis, CSC/NGO assistant dashboard, full RAG + vector DB + knowledge graph, custom model training.

### Home screen (5 actions)
Find Schemes · Check Eligibility · Understand a Notice · Scam Alerts · Forms Help. Persistent language toggle (EN / हिं / ಕನ್ನಡ) and voice controls on every screen.

## 7. Data models (Mongoose)

Seven collections from the docs **plus one recommended addition (`notifications`)** — see §17.

```js
// User  (anonymous profile OR registered account)
{
  deviceId: { type: String, index: true },          // anonymous UUID from localStorage
  name: String,
  phone: { type: String, unique: true, sparse: true },
  passwordHash: String,                              // only if registered
  state: String,
  category: String,
  language: { type: String, enum: ['en','hi','kn'], default: 'en' },
  createdAt: { type: Date, default: Date.now }
}

// Scheme
{
  title: String,
  department: String,
  state: String,                                     // "All India" or state name
  category: [String],
  eligibilityRules: [{
    field: String,        // 'age' | 'annualIncome' | 'category' | 'gender' | 'occupation' | 'state' | ...
    operator: String,     // 'equals' | 'lessThan' | 'greaterThan' | 'between' | 'in'
    value: Schema.Types.Mixed,
    label: String         // human-readable, e.g. "Annual family income below ₹2,50,000"
  }],
  originalText: String,
  simplifiedText: { type: Map, of: String },         // { en, hi, kn }
  sourceUrl: String,
  contentHash: String,                               // hash of originalText + rules, for cheap change detection
  lastScrapedAt: Date
}
// indexes: state, category, text index on title+originalText

// FormTemplate
{
  schemeId: { type: ObjectId, ref: 'Scheme' },
  title: String,
  fields: [{
    fieldName: String,
    description: { type: Map, of: String },          // per language, cached Gemini output
    example: String
  }],
  sourceUrl: String
}

// Notice
{
  userId: { type: ObjectId, ref: 'User', default: null },
  uploadedText: String,                              // see §17 privacy note (consider TTL / not storing)
  explanation: { type: Map, of: String },
  actionChecklist: [{ description: String, dueDate: Date, completed: { type: Boolean, default: false } }],
  createdAt: { type: Date, default: Date.now }
}

// ScamAlert
{
  title: String,
  description: { type: Map, of: String },
  sourceUrl: String,
  publishedAt: Date,
  matchedCategories: [String]
}

// Bookmark
{
  userId: { type: ObjectId, ref: 'User', required: true },
  itemType: { type: String, enum: ['scheme','form'] },
  itemId: ObjectId,
  savedAt: { type: Date, default: Date.now }
}
// unique compound index: { userId: 1, itemType: 1, itemId: 1 }

// ChangeRadarLog
{
  schemeId: { type: ObjectId, ref: 'Scheme' },
  previousVersion: Object,
  newVersion: Object,
  diffSummary: String,
  detectedAt: { type: Date, default: Date.now }
}

// Notification  (recommended 8th collection)
{
  userId: { type: ObjectId, ref: 'User' },           // works for anonymous profiles too (they have a User doc)
  type: { type: String, enum: ['scheme_change','scam_alert'] },
  refId: ObjectId,
  message: { type: Map, of: String },
  read: { type: Boolean, default: false },
  createdAt: { type: Date, default: Date.now }
}
```

Design rules: multilingual fields are `Map<lang,String>` (add languages with no schema change). `fields[]` and `actionChecklist[]` are embedded (composition). Cross-collection links are ObjectId references.

## 8. REST API

Base: `/api`. All JSON. Language passed as `?lang=en|hi|kn` or from profile.

| Method | Route | Auth | Purpose |
|---|---|---|---|
| POST | `/profile` | none | Create/update anonymous profile `{deviceId, state, category, language}` → returns profile |
| GET | `/profile/:deviceId` | none | Fetch profile |
| GET | `/schemes/search?q&state&category&lang` | none | Search + simplified results |
| GET | `/schemes/:id?lang` | none | Scheme detail (simplified + original + source) |
| GET | `/schemes/:id/questions` | none | Eligibility questions derived from `eligibilityRules` |
| POST | `/eligibility/check` | none | `{schemeId, answers, lang}` → per-criterion result + explanation |
| GET | `/forms?q&schemeId` | none | List/search forms |
| GET | `/forms/:id/guidance?lang` | none | Field-by-field guidance |
| POST | `/notices/explain` | none | `{text, lang, deviceId}` → explanation + checklist |
| PATCH | `/notices/:id/checklist/:index` | none | Toggle checklist item |
| GET | `/alerts?lang&category` | none | Personalized/public scam alerts |
| GET | `/notifications?deviceId` | none | Change Radar / scam notifications |
| PATCH | `/notifications/:id/read` | none | Mark read |
| POST | `/auth/register` | none | `{name, phone, password, deviceId}` → links profile to account, returns JWT |
| POST | `/auth/login` | none | → JWT |
| GET/POST/DELETE | `/bookmarks` | JWT | List / add / remove |
| POST | `/admin/scrape` | secret header | Manual scrape trigger (also used by scheduler) |

Standard error shape: `{ error: { code, message } }`. Rate-limit all Gemini-backed routes.

## 9. Feature logic & AI prompts

### 9.1 Gemini service (`services/gemini.js`)
One module wrapping all calls. Functions: `simplifyAndTranslate`, `explainEligibility`, `explainFormField`, `explainNotice`, `generateChecklist`, `translateAlert`. Requirements:
- API key server-side only (env var).
- Timeout + 1 retry; on failure return original text with a notice ("Simplified version unavailable").
- Ask for **JSON output** where structure is needed (checklist, notice).
- Cache results in MongoDB before returning.
- Language names passed explicitly (English / Hindi / Kannada).

### 9.2 Prompt rules (apply to all prompts)
```
You simplify Indian government information for low-literacy citizens.
Rules:
- Write in {LANGUAGE}, simple words, short sentences (about class 6 reading level).
- Do NOT add facts that are not in the source text.
- Keep every number, amount, date, age limit and document name EXACTLY as in the source.
- If something is unclear or missing in the source, say it is not mentioned.
- No legal advice. No guarantees of approval.
```
- **Scheme simplify:** input = scheme `originalText`; output = short summary + "Who can apply" + "Benefits" + "Documents needed" + "How to apply".
- **Eligibility explain:** input = scheme title + the **already computed** per-criterion results; output = plain explanation + "what you can do next". Prompt states: "Do not change the pass/fail results."
- **Form field:** input = field name + form title; output = meaning, what to write, example, where to get the document.
- **Notice:** input = notice text; output JSON `{ explanation, checklist: [{ description, dueDate|null }] }`. Prompt: "Only include due dates that appear in the notice."

### 9.3 Scheme search + simplify
1. Query Mongo: `state ∈ {profile.state, "All India"}` AND `category contains profile.category` AND text match on `q`.
2. For each hit, if `simplifiedText[lang]` exists use it; else call Gemini, save to `simplifiedText[lang]`.
3. Return `{ title, simplifiedText, originalText, sourceUrl }`.
4. Simplify lazily and in parallel with a concurrency cap (3–5); only simplify the top N results (e.g., 10) per request.

### 9.4 Eligibility rule engine (`services/eligibilityEngine.js`)
```js
function evaluateRule(rule, answer) {
  switch (rule.operator) {
    case 'equals':      return String(answer).toLowerCase() === String(rule.value).toLowerCase();
    case 'lessThan':    return Number(answer) < Number(rule.value);
    case 'greaterThan': return Number(answer) > Number(rule.value);
    case 'between':     return Number(answer) >= rule.value[0] && Number(answer) <= rule.value[1];
    case 'in':          return rule.value.map(v => String(v).toLowerCase()).includes(String(answer).toLowerCase());
    default:            return false;
  }
}
// checkEligibility(scheme, answers) -> { eligible, perCriterion:[{label, passed, yourAnswer}], missing:[labels] }
```
Missing answer = criterion marked "not answered" (not silently failed). Rules are curated per scheme (manual or semi-automatic extraction reviewed by hand). **Eligibility is never decided by the LLM.**

### 9.5 Forms guidance
Fetch form → for each field without `description[lang]`, call Gemini (batch all missing fields in **one** call returning JSON) → save → return list.

### 9.6 Notice-to-Action
Call Gemini once with JSON mode → validate JSON → save Notice (see privacy note §17) → return `{ explanation, checklist }`.

### 9.7 Scam alerts
Filter `matchedCategories` contains profile.category (or all for public showcase), sort by `publishedAt` desc, translate description lazily with cache.

### 9.8 Voice (client hooks)
- `useSpeechRecognition(lang)` → start/stop, transcript, error; maps `en→en-IN, hi→hi-IN, kn→kn-IN`.
- `useSpeechSynthesis(lang)` → speak(text), stop; picks a voice matching the locale; if none, show "Voice not available on this device".
- Always keep typed input as a fallback.
- Onboarding by voice: parse transcript against known state/category lists (fuzzy match), then show a confirmation screen before saving.

## 10. Scraping & Change Radar pipeline

**Principle: the app must work from curated seed data. Scraping is an enhancement, not a dependency.**

### 10.1 Seed first
Hand-curate `seed-data/schemes.json` (30–50 schemes: central + Karnataka), `forms.json` (10–20 forms), `alerts.json` (15–20 alerts). `npm run seed` loads them. This guarantees a demo even if scraping breaks.

### 10.2 Scrapers (`scripts/scrapers/*`)
- Before writing a scraper, open DevTools → Network on the source site and check for a **JSON API** the site itself calls — use that instead of HTML scraping if available. Check `robots.txt` and terms of use.
- Static pages: Axios + Cheerio. Only use Puppeteer if the page is JS-rendered.
- PDFs: download → `pdf-parse` → extract text.
- Each scraper returns normalized records: `{ type, title, sourceUrl, originalText, state, category, eligibilityRules? }`.
- Per-page try/catch: log failure, continue to next page.
- Polite: delay between requests, set a descriptive User-Agent, never hammer.

### 10.3 Change Radar (`services/changeRadar.js`)
```
processScrapedRecord(record):
  existing = find by sourceUrl
  if none -> insert, return
  newHash = hash(record.originalText + JSON.stringify(record.eligibilityRules))
  if newHash === existing.contentHash -> log "no change", return
  diff = summarize field-level changes (title, text, rules)
  save ChangeRadarLog {previousVersion, newVersion, diffSummary}
  update scheme; CLEAR simplifiedText cache (it is now stale)
  notifyMatchingUsers(record)
```
`notifyMatchingUsers`: find users where `state ∈ {scheme.state,"All India"}` AND `category ∈ scheme.category` (also users who bookmarked it) → create `Notification` docs (message per user language).

### 10.4 Scheduling (important — see §17)
Do **not** rely on `node-cron` inside a free Render web service (it sleeps and won't run). Use one of:
- **GitHub Actions** scheduled workflow (`on: schedule`) that runs `node scripts/scrape.js` against Atlas (recommended, free), or
- Render Cron Job, or an external pinger (cron-job.org) calling the protected `POST /api/admin/scrape`.
Frequency: 2–3×/day is plenty.

## 12. Security & privacy

- Gemini key and Mongo URI only in server env; never in client.
- helmet, CORS limited to the Vercel domain, rate limiting (stricter on AI routes), request size limits, input validation on every route.
- Passwords hashed with bcrypt (10–12 rounds); JWT short expiry; JWT only needed for bookmarks.
- Anonymous profiles hold only state/category/language — no PII.
- Always show source link; disclaimer on every AI screen: "Simplified by AI. Verify with the official source."
- Admin/scrape endpoint protected by secret header.
- No sensitive uploads stored beyond what is needed (see §17).

## 17. Known issues & decisions to settle (critical — read before building)

1. **Gemini model name.** Docs everywhere say "Gemini 1.5 Flash". Google has been retiring 1.5 models; check Google's current model list and set `GEMINI_MODEL` accordingly (a current Flash-tier model). Keep the model name in env, not hard-coded. Also check free-tier rate limits — they affect how much lazy simplification you can do per minute.
2. **node-cron on Render free tier will not run reliably** (service sleeps). Use GitHub Actions / Render Cron / external pinger (§10.4). The SRS text says node-cron; implementation can still use the same script, just triggered externally.
3. **Notification delivery for anonymous users.** SRS says Change Radar "notifies citizen profiles" but there is no login and no contact channel. MVP resolution: **in-app notification feed** keyed by `deviceId` (shown on next visit + unread badge). Add a `notifications` collection (8th). Optional later: web push, SMS/WhatsApp (Future Scope). Update the docs wording accordingly.
4. **Privacy contradiction.** SRS 3.5.2 says uploaded content is not stored beyond what's needed, but the `notices` schema stores `uploadedText`. Fix: don't store the raw text (store only explanation + checklist), or add a TTL index (e.g., auto-delete after 24h–7d). Pick one and update Chapter 5.
5. **Notice upload "image" vs OCR deferred.** OCR is out of scope. MVP options: (a) text paste only, or (b) send the image/PDF directly to Gemini's multimodal input (no separate OCR library). Option (b) is cheap to build; decide in Week 6.
6. **Scraping legality/fragility.** Check robots.txt/terms; prefer official JSON endpoints; keep scrapers polite; the app must still run from seed data. myScheme is JS-heavy — expect to need its underlying API or Puppeteer; Puppeteer is memory-heavy, so run it in GitHub Actions, not on the Render free web service.
7. **Eligibility rules need human curation.** Auto-extracting rules from scheme text with an LLM is error-prone. Curate rules manually for the demo schemes (verify against the official page); this is a quality point for the report.
8. **Language scope inconsistency.** Earlier synopsis framing said Kannada + English only; SRS says English, Hindi, Kannada. Build all three (cheap, since AI + i18n JSON), but make sure Kannada quality is the best-tested.
9. **Browser voice limits.** `kn-IN` recognition and Kannada TTS voices vary by browser/device; Chrome on Android is most reliable. Test early (Week 7–9) and keep Bhashini as fallback; always keep typed input.
10. **AI hallucination risk.** Mitigations already in design: prompt rules, preserve numbers/dates, always show original + source link, disclaimer. Add a manual spot-check pass before demo.
11. **Anonymous profile → account link.** On register, attach the existing `deviceId` profile to the new account so bookmarks/notifications carry over.
