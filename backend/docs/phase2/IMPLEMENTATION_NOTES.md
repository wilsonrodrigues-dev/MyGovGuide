# Implementation decisions and Phase 3 handoff

- Phase 2 stays backend-only. No website/design skill was needed because the task explicitly excludes the UI. No agents were delegated, external messages sent, services deployed or paid resources used.
- JavaScript ESM, Node 24, Express, Mongoose, Zod and the Node test runner keep the dependency footprint small. Native HTTPS is used so DNS resolution can be pinned after policy checks. Cheerio, rss-parser and pdf-parse implement established parsing behavior; csv-parse reads the actual evidence CSVs.
- Node engine metadata was checked using npm. The [Mongoose validation guide](https://mongoosejs.com/docs/validation.html) distinguishes document validation from unique indexes; both are tested. The [Node test runner documentation](https://nodejs.org/api/test.html) informed the built-in runner setup. Package-lock.json pins the actual installed dependency tree.
- Original documents/datasets remain in place; docs/phase1 is an index instead of a duplicate research archive. The two supplied JSON files were read before actual mappings were finalized. Missing original datasets are never generated or silently reconstructed from CSV.
- `import:phase1` requires all four roots. `import:available` is an explicit, reported partial import. URL-reference Source identities are supplemental and denied, not substitutes for the absent source registry. Full original source/notices mappings must be checked once those files arrive.
- Models share a small provenance/review envelope, with entity-specific fields and indexes, in `models/index.js`. Stable string IDs are both MongoDB `_id` values and unique public `id` values; references resolve to those IDs. A future API can retain original scheme IDs without an ObjectId-to-legacy lookup table.
- API fields for citizen views belong to a future projection from reviewed values, preserving original source and verification labels. Scheme/FormTemplate/Notice/ScamAlert models retain future-compatible semantics. The current API exposes aggregate health/status only.
- Immutable source version instances have entity/revision uniqueness and a source/hash lookup index. A return from B to earlier content A remains a distinct historical observation. Repeat A-A runs create neither a new version nor an event.
- Transactions are required instead of attempting best-effort writes on a standalone MongoDB. Each source batch either commits records, versions and review items together or rolls back. A separate local replica set leaves the existing database service alone.
- Access approval, content verification, publication rights and rule approval are independent. No source/eligibility approval was inferred from research, HTTP success or parsing. Site adapters can register through `registerSiteAdapter(sourceId, AdapterClass)` and inherit the common fetch/normalization/staging interface.
- Form classification is conservative: a bank consent-form reference or a governing-rule PDF with an unconfirmed blank form remains instructions-only. Field labels mentioning Aadhaar/mobile are metadata, never application data. Known sensitive data keys are rejected and rejection copies redacted.
- Dates and financial values are parsed only when formats/units are explicit. Missing, uncertain or historical windows remain research annotations. Research keyFacts are individually source-versioned but not treated as operative clauses.
- New observations never publish themselves. Verified values remain stored during source changes, release is withdrawn, caches are stale and rule readiness becomes incomplete. Review decisions require human identity, evidence, clauses and the observed version. A separate publication-evidence gate prevents research release.
- Scheduling is configured but commented out, and live collection defaults false. Runtime reports and no-op history make missing approvals visible without requiring MongoDB credentials for a safe no-op.

Before Phase 3: supply the missing JSON files and inspect their actual shapes; reconcile all source identities; obtain per-host access rights; review current operative clauses; approve publication rights; then build citizen-facing projections, three-state eligibility evaluation, translation caches, session ownership and authenticated operational tooling. These are not implied by a working internal research pipeline.
